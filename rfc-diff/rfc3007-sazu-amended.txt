Abstract

   This document proposes a method for performing secure Domain Name
   System (DNS) dynamic updates.  The method described here is intended
   to be flexible and useful while requiring as few changes to the
   protocol as possible.  The authentication of the dynamic update
   message is separate from later DNSSEC validation of the data.  Secure
   communication based on authenticated requests and transactions is
   used to provide authorization.  This revision additionally defines an
   externally-signed update policy (Section 4.5) under which the server
   verifies, rather than generates, the SIG records covering updated
   data.

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this
   document are to be interpreted as described in RFC 2119 [RFC2119].

1 - Introduction

   This document defines a means to secure dynamic updates of the Domain
   Name System (DNS), allowing only authorized sources to make changes
   to a zone's contents.  The existing unsecured dynamic update
   operations form the basis for this work.

   Familiarity with the DNS system [RFC1034, RFC1035] and dynamic update
   [RFC2136] is helpful and is assumed by this document.  In addition,
   knowledge of DNS security extensions [RFC2535], SIG(0) transaction
   security [RFC2535, RFC2931], and TSIG transaction security [RFC2845]
   is recommended.

   This document updates portions of RFC 2535, in particular section
   3.1.2, and RFC 2136.  This document obsoletes RFC 2137, an alternate
   proposal for secure dynamic update, due to implementation experience.
   Section 4.5 of this revision additionally defines an externally-
   signed update policy, in which the zone administrator MAY choose to
   have the server verify update-supplied SIG records instead of
   generating them from an online zone key.

1.1 - Overview of DNS Dynamic Update

   DNS dynamic update defines a new DNS opcode and a new interpretation
   of the DNS message if that opcode is used.  An update can specify
   insertions or deletions of data, along with prerequisites necessary
   for the updates to occur.  All tests and changes for a DNS update
   request are restricted to a single zone, and are performed at the
   primary server for the zone.  The primary server for a dynamic zone
   must increment the zone SOA serial number when an update occurs or
   before the next retrieval of the SOA.

1.2 - Overview of DNS Transaction Security

   Exchanges of DNS messages which include TSIG [RFC2845] or SIG(0)
   [RFC2535, RFC2931] records allow two DNS entities to authenticate DNS
   requests and responses sent between them.  A TSIG MAC (message
   authentication code) is derived from a shared secret, and a SIG(0) is
   generated from a private key whose public counterpart is stored in
   DNS.  In both cases, a record containing the message signature/MAC is
   included as the final resource record in a DNS message.  Keyed
   hashes, used in TSIG, are inexpensive to calculate and verify.
   Public key encryption, as used in SIG(0), is more scalable as the
   public keys are stored in DNS.

1.3 - Comparison of data authentication and message authentication

   Message based authentication, using TSIG or SIG(0), provides
   protection for the entire message with a single signing and single
   verification which, in the case of TSIG, is a relatively inexpensive
   MAC creation and check.  For update requests, this signature can
   establish, based on policy or key negotiation, the authority to make
   the request.

   DNSSEC SIG records can be used to protect the integrity of individual
   RRs or RRsets in a DNS message with the authority of the zone owner.
   However, this cannot sufficiently protect the dynamic update request.

   Using SIG records to secure RRsets in an update request is
   incompatible with the design of update, as described below, and would
   in any case require multiple expensive public key signatures and
   verifications.

   SIG records do not cover the message header, which includes record
   counts.  Therefore, it is possible to maliciously insert or remove
   RRsets in an update request without causing a verification failure.

   If SIG records were used to protect the prerequisite section, it
   would be impossible to determine whether the SIGs themselves were a
   prerequisite or simply used for validation.

   In the update section of an update request, signing requests to add
   an RRset is straightforward, and this signature could be permanently
   used to protect the data, as specified in [RFC2535].  However, if an
   RRset is deleted, there is no data for a SIG to cover.

1.4 - Data and message signatures

   As specified in [RFC3008], the DNSSEC validation process performed by
   a resolver MUST NOT process any non-zone keys unless local policy
   dictates otherwise.  When performing secure dynamic update, all zone
   data modified in a signed zone MUST be signed by a relevant zone key.
   This completely disassociates authentication of an update request
   from authentication of the data itself.

   The primary usefulness of host and user keys, with respect to DNSSEC,
   is to authenticate messages, including dynamic updates.  Thus, host
   and user keys MAY be used to generate SIG(0) records to authenticate
   updates and MAY be used in the TKEY [RFC2930] process to generate
   TSIG shared secrets.  In both cases, no SIG records generated by
   non-zone keys will be used in a DNSSEC validation process unless
   local policy dictates.

   Authentication of data, once it is present in DNS, only involves
   DNSSEC zone keys and signatures generated by them.

1.5 - Signatory strength

   [RFC2535, section 3.1.2] defines the signatory field of a key as the
   final 4 bits of the flags field, but does not define its value.  This
   proposal leaves this field undefined.  Updating [RFC2535], this field
   SHOULD be set to 0 in KEY records, and MUST be ignored.

2 - Authentication

   TSIG or SIG(0) records MUST be included in all secure dynamic update
   messages.  This allows the server to verifiably determine the
   originator of a message.  If the message contains authentication in
   the form of a SIG(0), the identity of the sender (that is, the
   principal) is the owner of the KEY RR that generated the SIG(0).  If
   the message contains a TSIG generated by a statically configured

   shared secret, the principal is the same as or derived from the
   shared secret name.  If the message contains a TSIG generated by a
   dynamically configured shared secret, the principal is the same as
   the one that authenticated the TKEY process; if the TKEY process was
   unauthenticated, no information is known about the principal, and the
   associated TSIG shared secret MUST NOT be used for secure dynamic
   update.

   SIG(0) signatures SHOULD NOT be generated by zone keys, since
   transactions are initiated by a host or user, not a zone.  This
   recommendation MAY be relaxed for a zone operating under the
   externally-signed update policy of Section 4.5: because that policy
   makes the update principal the sole source of both the transaction
   signature and the zone's data signatures by design, a zone key MAY
   also serve as the SIG(0) key for that zone's update transactions.

   DNSSEC SIG records (other than SIG(0)) MAY be included in an update
   message, but MUST NOT be used to authenticate the update request.

   If an update fails because it is signed with an unauthorized key, the
   server MUST indicate failure by returning a message with RCODE
   REFUSED.  Other TSIG, SIG(0), or dynamic update errors are returned
   as specified in the appropriate protocol description.

3 - Policy

   All policy is configured by the zone administrator and enforced by
   the zone's primary name server.  Policy dictates the authorized
   actions that an authenticated principal can take.  Policy checks are
   based on the principal and the desired action, where the principal is
   derived from the message signing key and applied to dynamic update
   messages signed with that key.

   The server's policy defines criteria which determine if the key used
   to sign the update is permitted to perform the requested updates.  By
   default, a principal MUST NOT be permitted to make any changes to
   zone data; any permissions MUST be enabled though configuration.

   The policy is fully implemented in the primary zone server's
   configuration for several reasons.  This removes limitations imposed
   by encoding policy into a fixed number of bits (such as the KEY RR's
   signatory field).  Policy is only relevant in the server applying it,
   so there is no reason to expose it.  Finally, a change in policy or a
   new type of policy should not affect the DNS protocol or data format,
   and should not cause interoperability failures.

3.1 - Standard policies

   Implementations SHOULD allow access control policies to use the
   principal as an authorization token, and MAY also allow policies to
   grant permission to a signed message regardless of principal.

   A common practice would be to restrict the permissions of a principal
   by domain name.  That is, a principal could be permitted to add,
   delete, or modify entries corresponding to one or more domain names.
   Implementations SHOULD allow per-name access control, and SHOULD
   provide a concise representation of the principal's own name, its
   subdomains, and all names in the zone.

   Additionally, a server SHOULD allow restricting updates by RR type,
   so that a principal could add, delete, or modify specific record
   types at certain names.  Implementations SHOULD allow per-type access
   control, and SHOULD provide concise representations of all types and
   all "user" types, where a user type is defined as one that does not
   affect the operation of DNS itself.

3.1.1 - User types

   User types include all data types except SOA, NS, SIG, and NXT.  SOA
   and NS records SHOULD NOT be modified by normal users, since these
   types create or modify delegation points.  The addition of SIG
   records can lead to attacks resulting in additional workload for
   resolvers, and the deletion of SIG records could lead to extra work
   for the server if the zone SIG was deleted.  Note that these records
   are not forbidden, but not recommended for normal users.

   NXT records MUST NOT be created, modified, or deleted by dynamic
   update, as their update may cause instability in the protocol.  This
   is an update to RFC 2136.

   Issues concerning updates of KEY records are discussed in the
   Security Considerations section.

3.2 - Additional policies

   Users are free to implement any policies.  Policies may be as
   specific or general as desired, and as complex as desired.  They may
   depend on the principal or any other characteristics of the signed
   message.

4 - Interaction with DNSSEC

   Although this protocol does not change the way updates to secure
   zones are processed, there are a number of issues that should be
   clarified.

4.1 - Adding SIGs

   An authorized update request MAY include SIG records with each RRset.
   Since SIG records (except SIG(0) records) MUST NOT be used for
   authentication of the update message, they are not required.

   If a principal is authorized to update SIG records and there are SIG
   records in the update, and the zone is not operating under the
   externally-signed update policy of Section 4.5, the SIG records are
   added without verification.  The server MAY examine SIG records and
   drop SIGs with a temporal validity period in the past.

   If the zone IS operating under the externally-signed update policy
   of Section 4.5, this subsection does not apply; SIG records are
   instead verified as specified there, and an update containing an
   unverifiable SIG record MUST be rejected in its entirety rather than
   added.

4.2 - Deleting SIGs

   If a principal is authorized to update SIG records and the update
   specifies the deletion of SIG records, the server MAY choose to
   override the authority and refuse the update.  For example, the
   server may allow all SIG records not generated by a zone key to be
   deleted.

4.3 - Non-explicit updates to SIGs

   If the updated zone is secured, the RRset affected by an update
   operation MUST, at the completion of the update, be signed in
   accordance with the zone's signing policy.  This will usually require
   one or more SIG records to be generated by one or more zone keys
   whose private components MUST be online [RFC3008].  Section 4.5
   defines an alternative signing policy, externally-signed update, in
   which this requirement is instead satisfied by the server verifying
   SIG records supplied by the update principal; a zone operating under
   that policy has no zone private key material online at the server.

   When the contents of an RRset are updated, the server MAY delete all
   associated SIG records, since they will no longer be valid.  The
   server MUST NOT do so unconditionally for a zone operating under the
   externally-signed update policy of Section 4.5: since the server
   holds no zone key with which to replace them, deletion without a
   verified replacement in the same transaction would leave the RRset
   unsigned.

4.4 - Effects on the zone

   If any changes are made, the server MUST, if necessary, generate a
   new SOA record and new NXT records, and sign these with the
   appropriate zone keys.  Changes to NXT records by secure dynamic
   update are explicitly forbidden.  SOA updates are allowed, since the
   maintenance of SOA parameters is outside of the scope of the DNS
   protocol.  For a zone operating under the externally-signed update
   policy of Section 4.5, the new SOA and any new NXT (or NSEC/NSEC3)
   records, and their SIGs, are instead supplied and verified as part
   of the same update transaction; see Section 4.5.

4.5 - Externally-signed updates

   A zone administrator MAY, as a matter of policy (Section 3),
   configure a zone such that the server verifies SIG records supplied
   by the update principal instead of generating them itself.  This
   policy is OPTIONAL to implement and OPTIONAL to enable per zone; a
   server or zone not configured for it behaves exactly as specified
   elsewhere in this document.

   4.5.1 - Applicability

      This policy MAY be enabled only for a zone whose signing key(s)
      are not held online at the server.  It is intended for deployments
      in which the party authorized to update the zone (Section 3) also
      holds the zone's DNSSEC signing key(s), and signs data before it
      is sent, rather than delegating signing to the server as described
      in Section 4.3.

   4.5.2 - Transaction authentication

      Section 2 continues to apply: TSIG or SIG(0) MUST be used to
      authenticate the update message, and the principal so
      authenticated is checked against policy (Section 3) as usual.  Per
      the amendment to Section 2 above, the SIG(0) key MAY be a zone key
      when this policy is in effect; the SIG(0) signer name is then the
      zone apex, and a server MUST reject a SIG(0) naming any other
      signer.  A server SHOULD bound the SIG(0) validity period
      (expiration minus inception) it accepts; [SAZU] uses one hour plus
      clock skew.  How a server first associates a principal's key with
      authorization to update a given zone is a matter of server policy
      and is outside the scope of this document; [SAZU] defines one such
      mechanism.

   4.5.3 - Verification of supplied SIG records

      For each RRset added or modified by the update that is
      authoritative data of the zone, and for any SOA or NXT/NSEC/NSEC3
      record supplied under Section 4.4, an accompanying SIG (RRSIG)
      record MUST be present and MUST be verified by the
      server against a DNSKEY the server currently trusts for the zone
      before the update is applied.  Verification MUST be performed
      against the RRset as it will exist in the zone once the update is
      applied, not merely against the records present in the update.
      Verification MUST confirm that:

      (a)  the SIG's temporal validity period (inception and expiration)
           is currently valid;

      (b)  the SIG's algorithm is acceptable under the server's
           configured policy;

      (c)  the SIG's owner name, type covered, and RDATA correspond
           exactly to the RRset it accompanies;

      (d)  the signature itself is cryptographically valid for that
           RRset under the referenced DNSKEY; and

      (e)  for the zone apex KEY (DNSKEY) RRset, the referenced DNSKEY
           is one matched against a DS record in the parent zone per
           Section 4.5.4, since validating resolvers accept no other
           signer for that RRset.

      If any supplied SIG fails verification under (a) through (e), or
      is absent where required by this section, the server MUST reject
      the update in its entirety and MUST NOT apply any part of it.
      This is a change from Section 4.1, under which an unverified SIG
      is ordinarily added rather than checked.

      The NS RRset at a delegation point and glue address records below
      it are not authoritative data of the zone and are not signed
      [RFC4035] Section 2.2; they need no SIG under this section, and an
      update carrying a SIG over them MUST be rejected.

   4.5.4 - Key rollover

      An update MAY include a new DNSKEY record for the zone.  A DNSKEY
      so added MUST itself be covered by a SIG verified per Section
      4.5.3 under the zone's DS-matched DNSKEY, except for a DS-matched
      DNSKEY itself, which is trusted on receipt of an authenticated
      update for that zone if and only if it matches a DS record
      published for the zone in the parent zone, validated from a
      configured trust anchor, per the mechanism defined in [SAZU].
      The update that establishes a DS-matched DNSKEY MAY additionally
      include further DNSKEYs not themselves matched against a DS
      record, provided they are covered, in that same update, by a SIG
      verified per Section 4.5.3 under the DS-matched DNSKEY; such keys
      are trusted from that point on the same basis as any other DNSKEY
      added under the DS-matched key.  Per [SAZU], this pairing is
      intended so that the DS-matched key need be used only to
      establish trust, to change the zone's key set, and to re-establish
      trust on a later rollover, while the further keys authenticate
      and sign ordinary updates without it.

      A later update that introduces a different DS-matched DNSKEY, and
      removes the previous one, replaces the previous DS-matched key
      once its own DS match succeeds; keys added under the previous
      DS-matched key remain trusted.  Such an update is expected to
      follow the double-DS procedure of [RFC6781] Section 4.1.2, so
      that validating resolvers are not affected by the change.  A
      server MAY delay such a replacement unless the update also
      carries a SIG over the new key set, verified per Section 4.5.3
      under the previous DS-matched DNSKEY; [SAZU] requires a delay
      (a hold-down) in that case, so that control of the parent zone's
      DS record alone does not transfer control of the zone at once.

   4.5.5 - Update semantics

      Because the server cannot sign, it cannot repair a zone that an
      update leaves inconsistent: an RRset whose SIG no longer covers
      it, or an NSEC/NSEC3 chain that no longer describes the zone.  A
      zone under this policy therefore changes content only by complete
      replacement, which modifies the processing of [RFC2136] as
      follows:

      (a)  An update that adds the zone's apex SOA RR is a replacement
           of the zone: the server removes every RRset of the zone
           except the apex DNSKEY (KEY) RRset and its SIGs, and then
           adds the update's RRs.  It carries the zone's complete
           content, including a complete NSEC or NSEC3 chain as defined
           by [RFC4034] Section 4 and [RFC5155] Section 7.1, and MUST
           NOT carry deletions other than of apex DNSKEY RRs.  This
           replaces the per-RR processing of [RFC2136] Section 3.4.2 for
           such updates.

      (b)  An update that would change zone content other than the apex
           DNSKEY RRset without adding the apex SOA MUST be rejected
           (REFUSED).

      (c)  [RFC2136] Section 3.6 requires the server to increment the
           SOA serial after an update.  Under this policy the server
           MUST NOT change the SOA RR, which it cannot sign; instead the
           SOA serial supplied in a replacement MUST be greater than the
           zone's current serial in the sense of [RFC1982], and an
           update whose serial is not MUST be rejected.  An update that
           changes only the apex DNSKEY RRset leaves the SOA unchanged.

      (d)  The replacement MUST be a valid zone: all RRs of an RRset
           have the same TTL ([RFC2181] Section 5.2), a name owning a
           CNAME RR owns no other data except SIG (RRSIG) and NSEC RRs
           ([RFC2181] Section 10.1, [RFC4035] Section 2.5), and no name
           exists below a DNAME RR ([RFC6672] Section 2.4).  Where
           [RFC2136] Section 3.4.2.2 silently ignores a conflicting
           CNAME update, a server under this policy MUST instead reject
           the update, since a silently dropped RR would leave the
           supplied NSEC/NSEC3 chain describing data the zone does not
           hold.

      (e)  A change to the apex DNSKEY RRset MUST carry the complete
           resulting RRset, so that Section 4.5.3 can verify its SIG
           against the RRset as it will be served.

      The prescan of [RFC2136] Sections 3.2.1 and 3.4.1.3 applies
      unchanged.  Queries are answered from the replaced zone as by any
      authoritative server; the server MUST NOT synthesize or sign
      records, including denial-of-existence records.

   4.5.6 - Control data and the version prerequisite

      [SAZU] carries control data that is not zone content (a contact
      address, a decommission request, the cancellation of a pending
      key replacement) as TXT RRs at reserved owner names below the
      zone apex ("_sazu-contact", "_sazu-decommission",
      "_sazu-cancel-rollover").  Such RRs are authenticated by the
      transaction signature alone, are removed from the update before
      it is processed as zone data, and are never served.

      To make each change to the zone's keys or control data apply at
      most once, the server maintains a per-zone version number,
      increments it with every such change, and publishes it, unsigned
      and outside the zone's signed data, as a TXT RR at
      "_sazu-version" below the zone apex.  An update making such a
      change MUST carry an [RFC2136] Section 2.4.2 "RRset exists
      (value dependent)" prerequisite on that RR with the current
      value.  The prerequisite is evaluated against the server's
      version, which is a use of Section 2.4.2 against data the server
      maintains rather than data an update supplied; an update MUST
      NOT add, delete or otherwise change the RR itself.

   4.5.7 - Transport and responses

      An update that would establish or replace a DS-matched DNSKEY
      causes the server to query the parent zone's chain of trust, and
      MUST NOT be accepted over a transport without source-address
      validation, such as UDP.  An update MAY be carried by DNS over
      HTTPS [RFC8484]; the server verifies SIG(0) over the DNS message
      bytes exactly as received in the request body.

      Response codes are those of [RFC2136] Section 2.6 and Section 2
      of this document: in particular REFUSED for an update signed by a
      key not authorized for it and for an update rejected under
      Sections 4.5.3 through 4.5.6.  A server SHOULD report the specific
      reason for a rejection in an Extended DNS Error [RFC8914] when the
      request carries EDNS(0) [RFC6891]; [SAZU] defines the reasons.

5 - Security Considerations

   This document requires that a zone key and possibly other
   cryptographic secret material be held in an on-line, network-
   connected host, most likely a name server.  This material is at the
   mercy of host security to remain a secret.  Exposing this secret puts
   DNS data at risk of masquerade attacks.  The data at risk is that in
   both zones served by the machine and delegated from this machine.
   This requirement does not apply to a zone operating under the
   externally-signed update policy of Section 4.5, whose DS-matched
   DNSKEY (Section 4.5.4) need never be held on any network-connected
   host; that policy instead depends entirely on the server's Section
   4.5.3 verification being implemented correctly and applied to every
   update without exception, since a server that skips or weakens this
   check would accept and serve unauthenticated data while appearing, to
   an operator who has not audited it, to be enforcing the same
   guarantee as Section 4.3.  A further DNSKEY established alongside the
   DS-matched one under Section 4.5.4 MAY reasonably be held on a
   network-connected host used only to authenticate and sign ordinary
   updates: per [SAZU], its exposure is recoverable by an update
   authenticated under the DS-matched key, requiring no action at the
   parent zone, which is not true of the DS-matched key itself.  The
   DS-matched key SHOULD be held to the same offline standard this
   section otherwise requires, regardless of whether a further key is
   in use.
